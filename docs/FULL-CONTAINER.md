# Полный запуск в Docker

Требуются Docker Desktop с Linux Engine (Windows: WSL2) или Docker Engine с
Compose v2.24.4+, а также Node.js для launcher-скрипта. Visual Studio и Webots
на хосте для этого режима не нужны. Если Node.js ставить нельзя, ниже остаются
ручные команды Docker Compose.

Из корня репозитория:

```sh
npm install
npm run start:container
```

Откройте http://127.0.0.1:8080/dashboard и выберите вкладку «Симуляция» в центре. Кнопка разворачивания увеличивает сцену почти на всё окно. Переключение вкладок и разворачивание сохраняют один экземпляр просмотрщика. Камера робота отдельно отображается в телеметрии; после обрыва просмотрщик пытается подключиться снова. Управление маршрутами выполняется кнопками планировщика.

Работают шесть контейнеров: frontend, planning, route, telemetry, gateway, simulator. Одноразовый init-secret создаёт токен в Docker volume и успешно завершается — статус Exited (0) для него нормален. Внутренний адрес gateway — `http://gateway:9004`; секрет не передаётся браузеру. Никакие процессы проекта на Windows не запускаются.

Launcher проверяет доступ Docker к `/dev/dxg`, X11-сокету WSLg и графическим
библиотекам. Если они доступны, Webots использует аппаратный OpenGL; иначе
запускается переносимый режим Xvfb/Mesa на CPU. Принудительный выбор:
`npm run start:container -- --cpu` или `npm run start:container -- --gpu`.
В открытой панели симуляции есть кнопки «Обычная» и «Максимальная» скорость.
[Настройка CPU/GPU, ограничения и замеры](SIMULATION-PERFORMANCE.md).

Контроллер собирается GCC в образе. Ресурсы нашего мира кэшируются при сборке; изменение мира может потребовать обновления `docker/cache-webots-assets.py` для динамически формируемых URL текстур. W3D проходит через nginx `/simulation/`; официальный просмотрщик R2025a, WASM и текстуры поставляются внутри frontend-образа. При добавлении текстур дополните `docker/webots-viewer-assets.json`. Браузеру нужен WebGL2. Webots работает с `--no-rendering`: внешний вид рисует браузер, а камеру робота — симулятор. Порт 1234 опубликован на localhost только для диагностики.

## Данные и остановка

```sh
docker compose -p gpo-full -f compose.yaml -f compose.simulator.yaml down
```

Без `-v` сохраняются миссии, журнал gateway, файлы симулятора и токен. Общий volume `simulator-state` доступен только gateway и Webots. Журнал gateway хранится в отдельном вложенном volume. При первом старте создаётся пустой маршрут, робот ожидает команду пользователя. Старый маршрут автоматически не возобновляется; незавершённую миссию можно отменить после старта контроллера.

Не запускайте одновременно полный и Windows-режим: они используют одни и те же localhost-порты. Windows-режим `npm start` остаётся доступен по инструкции в DOCKER.md. Его базы и файлы автоматически в полный режим не мигрируют.

## Проверка

```sh
docker compose -p gpo-full -f compose.yaml -f compose.simulator.yaml ps --all
docker compose -p gpo-full -f compose.yaml -f compose.simulator.yaml logs --tail 50 simulator
```

Готовность simulator проверяется по свежему `robot_state.json`, записанному после старта контейнера, и конечным координатам базы. Ошибка отдельной миссии не делает живой симулятор `unhealthy`. Отсутствие или повреждение телеметрии и остановка её обновления дольше 15 секунд делают проверку неуспешной. Пауза Webots также останавливает обновления контроллера; для восстановления readiness возобновите симуляцию. `unhealthy` не означает автоматический перезапуск: restart policy действует при завершении процесса. Для диагностики зависания сначала сохраните логи.

## Обновление после изменения кода

```sh
git pull
npm ci
npm run start:container
```

Обычный запуск всегда выполняет `docker compose build`, затем пересоздаёт сервисы,
образы которых изменились, и ждёт их готовности. Docker использует кэш зависимостей,
но изменения в `src`, `shared`, `bridge` и исходниках контроллера пересобираются.
Контроллер Linux собирается из C++; локальные `.exe`, `.obj`, Linux-бинарник,
каталоги сборки, временные файлы и заметки в контекст не попадают. Volumes сохраняются.
`--no-build` используйте только для повторного запуска уже собранной версии.
Простой `docker compose restart` использует старые контейнеры и код не обновляет.

Launcher записывает Git-ревизию в OCI-метку каждого образа. `-dirty` означает,
что сборка включает незакоммиченные изменения; `unknown` — архив без Git.
Для ручной Compose-сборки можно задать `GPO_SOURCE_REVISION` самостоятельно.
Метка служит справкой о сборке, а не контрольной суммой незакоммиченных файлов.

```sh
docker image inspect gpo-frontend:local gpo-service:local gpo-webots:local --format '{{.RepoTags}} {{index .Config.Labels "org.opencontainers.image.revision"}}'
```

При недоступном Docker Engine launcher завершает проверку с подсказкой до сборки.
После неуспешного ожидания готовности он выводит состояние сервисов и последние логи.
Секреты и volumes автоматически не удаляются. Если Docker Desktop сам показывает
внутреннюю ошибку, закройте его штатно и запустите снова; сброс к заводским настройкам
для обычного обновления проекта не нужен.

Для разработчика: `npm run test:container` запускает отдельный временный стек из собранных образов, проверяет смешанный порядок точек, камеру, W3D, локальный WASM, физическое выполнение маршрута, восстановление route после SIGKILL, отмену после перезапуска simulator, перенос большой коробки и PICK_BOX следом за ней, движение вперёд с грузом. При ошибке сохраняет телеметрию в `output/container-smoke-failure.json` и выводит логи. Затем удаляет только собственные тестовые контейнеры и volumes. Перед тестом освободите порты, остановив пользовательский стек. Python-проверки healthcheck запускаются командой `python -m unittest discover -s docker -p 'test_*.py'`.

## Ресурсы и ограничения

Базовый режим использует программный OpenGL/Mesa, GPU не обязателен. Он требует заметного CPU; плавность зависит от машины. Webots предупреждает о программном рендеринге и уменьшает качество эффектов. Это ожидаемо, но необходимость аппаратного ускорения оценивается по фактической скорости симуляции. Это локальная однопользовательская конфигурация; интернет-публикация, аутентификация пользователей и отдельные миры для разных пользователей требуют дополнительной реализации.
