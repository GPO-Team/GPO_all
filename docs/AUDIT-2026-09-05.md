# Аудит GPO — 5 сентября 2026

**Вывод: у проекта содержательная инженерная база, но текущая версия не готова к стабильной демонстрации полного сценария и эксплуатации.** Основной сценарий «поставить точки → построить → отправить» сейчас сломан на уровне сборки зависимостей React-хуков. После его исправления останутся независимые дефекты native solver, обмена с контроллером и энергетической модели.

Аудит выполнен лично основным агентом. После просьбы работать без субагентов помощники остановлены; их результаты в отчёте не использованы. Код приложения не исправлялся.

Рассмотрены все основные подсистемы: React-композиция и редакторы, геометрия и маршрутизация, энергия и зарядки, импорт/экспорт, телеметрия, shared-контракты, HTTP/WebSocket bridge, файловый обмен, C++ solver, жизненный цикл и навигация C-контроллера, сенсоры/карты, сборка, Docker и тесты. Приоритет ручного чтения — точки входа, границы подсистем, критические алгоритмы и обработка отказов. Это аудит подсистем и основных потоков, а не утверждение о формальной проверке каждой строки или отсутствии других ошибок.

Проверки выполнены на Windows, Node.js 22.19.0, MSVC и установленном Webots SDK. Браузер проверен на 1280×720 и 390×844. Его соединения перехвачены, чтобы действия аудита не записывали команды в текущую сцену; эти проверки не считаются сквозными тестами робота. Диагностические проверки bridge использовали отдельный сервер на случайном loopback-порту и тестовое хранилище. C-проверки использовали отдельные временные файлы.

## Подтверждённые проблемы

Приоритет P1 — исправить до следующей полноценной демонстрации; P2 — устранить до устойчивой эксплуатации. Нумерация нужна для дальнейшего отслеживания.

### 1. P1 — «Построить» и «Отправить» падают из-за отсутствующих аргументов

### 2. P1 — native solver обращается за границы массива на двух точках

[tour_operations.cpp:98](C:/GPO_nimmwee/native/src/tour_operations.cpp:98), [tour_operations.cpp:122](C:/GPO_nimmwee/native/src/tour_operations.cpp:122), [ga_tabu.cpp:66](C:/GPO_nimmwee/native/src/ga_tabu.cpp:66).

При длине порядка 2 код выбирает `left=1`, затем `right=2`: `uniform_int` возвращает нижнюю границу даже при перевёрнутом диапазоне. Следующая перестановка выходит за границы вектора.

Проверен TSP `(0,0), (1,0)`, seed 1337, стандартные параметры: `ga_tabu`, `otshig`, `cuckoo` завершаются с ошибкой; `rasseivanie` возвращает ожидаемый цикл длиной 2. Для GA код процесса `3221225477 / 0xC0000005` — access violation. При этом интерфейс считает две точки достаточными.

Исправление: прямое решение для малого числа точек и защита операций перестановки; регрессии на 0/1/2/3 точках для всех алгоритмов. Текущий [route_solver_service_test.cpp:5](C:/GPO_nimmwee/native/tests/route_solver_service_test.cpp:5) проверяет лишь пустой и одноточечный случаи.

Также не копируются `postcss.config.js` и `tailwind.config.js`: после устранения ошибки импортов необходимо проверить обработку Tailwind в самом контейнере, а не только успешный выход сборки. Исправление: полный набор build inputs и проверка готовой страницы из контейнера.

[controller_io.cpp:18](C:/GPO_nimmwee/webots/controllers/youbot_web/controller_io.cpp:18) возвращает `st_mtime` в секундах. Исправление: явная версия/идентификатор команды и подтверждение применения; как минимум точный timestamp или контроль содержимого с повтором после ошибки чтения.

### 5. P1 — bridge и контроллер допускают разные размеры данных

Исправление: единые лимиты в shared-контракте, проверка после всех обходов/зарядок, явное отклонение превышений контроллером. Учитывать замыкание TSP и дополнительные обходные точки.

### 6. P2 — повторная отправка идентичного маршрута не запускает его заново

[controller_route_zone_service.cpp:99](C:/GPO_nimmwee/webots/controllers/youbot_web/controller_route_zone_service.cpp:99) считает маршрут новым только при отличии координат/heading. Воспроизведено: тот же CSV с новой секундной отметкой прочитан успешно, но `route_changed=0`.

Поэтому явный повторный запуск после завершения не отличается от обновления состояния. Исправление: отделить «установить маршрут» от «начать выполнение», сохранять идентификатор запуска.

### 7. P1 — WebSocket принимает команды с произвольным Origin

[route-server.cjs:19](C:/GPO_nimmwee/bridge/servers/route-server.cjs:19): нет проверки Origin и аутентификации, роль определяется строкой URL. Изолированное подключение с `Origin: https://untrusted.example` принято как UI-клиент. Сервер способен принять изменяющую состояние команду от такого клиента.

Loopback и loopback-публикация Docker-портов — полезные ограничения, но не авторизация. Возможность обращения из конкретного браузера дополнительно зависит от его политики доступа к локальной сети; сам сервер её не обеспечивает. Аналогично стоит ограничить доступ к telemetry и wildcard CORS solver API.

Исправление для локального стенда: список разрешённых Origin, session token, различение прав UI и контроллера. Публичное сетевое размещение до этого не готово.

### 8. P2 — невалидная команда всё равно пересылается контроллеру, UI не получает отказ

Текущий Webots-путь использует файлы, поэтому это не доказательство исполнения невалидного WS-маршрута именно C-контроллером. Но серверный контракт нарушен, а при ошибке записи файлов UI тоже не получает отказ. [usePlannerRouteSender.js:79](C:/GPO_nimmwee/src/features/planner/hooks/usePlannerRouteSender.js:79) сообщает успех и запускает таймер сразу после `socket.send`, без подтверждения записи или принятия роботом.

Исправление: прекращать обработку при ошибке; ACK/NACK по requestId; отдельные состояния «отправлено», «сохранено», «принято», «выполняется».

### 9. P2 — план зарядок допускает недостаточный запас энергии

[chargingPlannerLegs.js:49](C:/GPO_nimmwee/src/features/planner/model/chargingPlannerLegs.js:49) оценивает энергию каждого ребра отдельно; поворот между рёбрами не вычитается из остатка. ### 10. P2 — расход покрытия определяется только серединой сегмента

## Архитектура, модель и качество продукта

**Сильные стороны.** Есть реальная функциональная декомпозиция: UI, модели, транспорт, файловое хранилище и native solver разделены; C-контроллер имеет тестируемые модули навигации, геометрии и сенсоров. Координатный контракт выделен. Solver запускается отдельным процессом с таймаутом 30 секунд и ограничением двух параллельных расчётов. Есть лимит HTTP-body и валидация чисел. JSON/Excel импорт отделён от интерфейса. Dashboard и SheetJS загружаются лениво: текущие gzip-размеры примерно 75.5 КБ основной JS, 37.6 КБ Dashboard, 163 КБ SheetJS. Это разумное разделение нагрузки.

**Избыточное число промежуточных обёрток.** В UI множество хуков только перекладывают один большой набор зависимостей в другой. Дефект №1 находится именно на такой границе. В C есть аналогичные слои service/runtime/adapter; сами по себе они допустимы, но их польза должна измеряться ясностью владения состоянием, а не числом маленьких файлов. Важнее добавить контрактные проверки, чем продолжать дробление.

**Тестов много, но уверенность не соответствует их числу.** Компонентные тесты девяти sidebar-секций используют `renderToStaticMarkup`: проверяют текст и HTML, а не клики и эффекты. Архитектурные проверки часто ищут строки импортов и имена файлов. Они не поймали отсутствие аргументов основного хука и неполный Dockerfile. Bridge smoke проверяет health и одну задачу на трёх точках, не маршрут UI → файл → controller → подтверждение. Native service test не проверяет двухточечный случай. CI-конфигурация в отслеживаемых файлах отсутствует. Нужны сценарные тесты, а не просто увеличение общего счётчика.

**Оптимальность маршрута ограничена.** C++ оптимизирует евклидовы расстояния; препятствия и зарядки добавляются позднее в JS. Это может давать допустимый обход, но не гарантирует хороший порядок посещения для итоговой стоимости с зонами и энергией. Эвристики не обязаны выдавать глобальный оптимум. Для оценки «насколько хорош» нужен воспроизводимый набор задач, эталон для малых размеров, несколько seed и метрики итогового пути, времени расчёта и допустимости. Сейчас таких результатов в репозитории не представлено.

**Энергия и покрытия пока являются моделью планирования.** Передаваемый маршрут содержит координаты, но не операции зарядки/время зарядки; физическая зарядка и состояние батареи не входят в проверенный контур исполнения. Покрытия в [controller_webots_simulation_format.cpp:85](C:/GPO_nimmwee/webots/controllers/youbot_web/controller_webots_simulation_format.cpp:85) создаются как визуальные `Pose/Shape`; сам этот код не задаёт им различное трение. [controller_motion_profile.cpp:66](C:/GPO_nimmwee/webots/controllers/youbot_web/controller_motion_profile.cpp:66) ограничивает линейную скорость по общему профилю, не по текущему полигону покрытия. Поэтому UI-значения «факт»/«лимит по покрытию» нельзя считать измеренной физикой робота. Для исследовательского стенда допустимо, если явно назвать допущения и калибровать модель.

**Эксплуатация и наблюдаемость.** WebSocket connected отражает соединение с bridge, а не свежесть данных робота. Нужны возраст последней телеметрии, идентификатор активного маршрута и понятный отказ контроллера. Таймер UI использует `Date.now`, тогда как headless Webots настроен на `--mode=fast`; сравнение его с плановым временем смешивает реальное и симуляционное время. Для режимов исполнения нужны явные остановка/пауза/возобновление; текущая очистка точек не является остановкой робота.

**Интерфейс.** На настольном экране карта рисуется, точки добавляются/очищаются, панели визуально последовательны. Но обе панели занимают большую часть ширины, основная кнопка запуска требует прокрутки, подписи карты мелкие. При 390 px фиксированные панели шириной 310+330 px практически вытесняют карту; мобильный режим неудобен. Canvas управляется мышью и не имеет полноценного клавиатурного/доступного редактора. Стоит определить минимальную поддерживаемую ширину либо добавить адаптивные панели. [Desktop](C:/GPO_nimmwee/docs/audit-2026-09-05/desktop.png), [Mobile](C:/GPO_nimmwee/docs/audit-2026-09-05/mobile.png).

**Сохранение работы.** Полный план живёт преимущественно в React state; localStorage сохраняет скорость и панели. Перезагрузка теряет точки и зоны, а начальная синхронизация может переписать состояние bridge пустыми зонами. Импорт графа и PNG-экспорт карты не заменяют сохранение/восстановление проекта. Это существенно для регулярного использования.

**Документация.** README полезнее AGENTS.md: последний ошибочно утверждает, что нет тестового runner и Git-истории. README по-прежнему рекомендует полный Docker-сценарий, который блокируется №3. Нужны актуальный список ограничений, описание реального файлового транспорта Webots и воспроизводимый запуск с проверкой готовности каждого компонента.

## Оценка готовности и порядок работ

| Область | Оценка |
|---|---|
| Инженерная база и объём реализации | Хорошая основа для учебного/исследовательского стенда |
| Основной сценарий пользователя | Не готов: два действия падают до сетевого запроса |
| Надёжность обмена | Недостаточна: нет подтверждённых версий команд, есть потери и обрезания |
| Расчёты и физическая достоверность | Есть полезная модель, но найдены ошибки и не подтверждена калибровка |
| Развёртывание | Локальные сборки работают; Docker требует исправления и проверки |
| Тестирование | Сильная начальная база модульных тестов, слабая проверка интеграции |
| Готовность к внешнему использованию | Не готов |

Процент готовности без согласованного перечня требований был бы выдуманным. Практический статус — **развиваемый прототип с блокирующими регрессиями**, который имеет смысл доводить, а не переписывать целиком.

Порядок исправлений:

1. Восстановить основной UI-поток (№1), добавить настоящий сценарный тест, закрыть двухточечный native crash (№2).
2. Исправить Docker inputs (№3) и реально собрать/открыть контейнерный фронтенд.
3. Сделать надёжный протокол исполнения: единые лимиты, атомарная запись, версии команд, ACK/NACK, повторная синхронизация и явный повторный запуск (№4–8, №11–13).
4. Исправить энергетический расчёт и устаревшие async-результаты (№9–10, №14); проверить базовые маршруты, пограничные запасы, покрытия и зарядки.
5. Провести сквозные Webots-прогоны: обычный маршрут, повторный запуск, препятствие, смена зон, недостижимая цель, перезапуск bridge/контроллера, отключение телеметрии. Проверять фактический результат по идентификатору миссии.
6. Закрепить проверки в CI, затем улучшать сохранение проектов, UX, адаптивность и метрики качества алгоритмов.

Критерий готовности к демонстрации: на чистом запуске пользователь проходит основной сценарий без консольных ошибок, контроллер подтверждает именно отправленную версию и завершает маршрут; перезапуск и повторная отправка ведут себя предсказуемо. Сейчас этот критерий не выполнен.
