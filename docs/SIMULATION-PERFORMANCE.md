# Webots: CPU, GPU и скорость симуляции

Физика и C-контроллер выполняются на CPU. GPU ускоряет OpenGL (сцену и
графические датчики), освобождая CPU. Перенос физики Webots на CUDA не выполняется.
Оба режима сохраняют камеру робота. Внешний вид передаётся по W3D и рисуется
в браузере через WebGL2. Webots запускается с `--stream=w3d --no-rendering`:
основное окно не рисуется на сервере, но графические датчики продолжают работать.

## Запуск без видеокарты

Из корня проекта, при работающем Docker с Linux Engine:

```powershell
docker compose -p gpo-full -f compose.yaml -f compose.simulator.yaml up --build -d --wait --wait-timeout 180
```

Это переносимый CPU-режим с Xvfb и программным Mesa. Не требует NVIDIA,
WSLg, `/dev/dxg` или GPU-драйверов. Интерфейс: http://127.0.0.1:8080/dashboard.

## GPU на Windows / Docker Desktop / WSL2

Обычный запуск автоматически выбирает этот режим, если Docker видит WSLg GPU:

```powershell
npm run start:container
```

Для явной диагностики GPU можно потребовать его без отката:

```powershell
npm run start:container -- --gpu
```

Ручной эквивалент:

```powershell
docker compose -p gpo-full -f compose.yaml -f compose.simulator.yaml -f compose.simulator.gpu-wslg.yaml up --build -d --wait --wait-timeout 180
```

Нужны работающий WSLg и Windows-драйвер с поддержкой WSL GPU. Проверено на RTX
3070 Ti. Дополнительный Compose-файл передаёт графический сокет, `/dev/dxg` и
библиотеки WSL в `simulator`. Остальные сервисы не используют GPU.

Проверка:

```powershell
docker compose -p gpo-full -f compose.yaml -f compose.simulator.yaml -f compose.simulator.gpu-wslg.yaml logs simulator
docker exec gpo-full-simulator-1 cat /tmp/webots-renderer.log
```

Ожидается `Accelerated: yes` и `D3D12 (NVIDIA GeForce RTX 3070 Ti)` либо другой
аппаратный адаптер. `llvmpipe`/`softpipe` означают CPU. Успешный `nvidia-smi`
сам по себе не подтверждает ускорение OpenGL. Предупреждение Webots R2025a о
производителе `Microsoft Corporation` возможно и при аппаратном D3D12: сверяйте
его с renderer и замерами, а не только с этим предупреждением.

Пути по умолчанию относятся к Docker Desktop. Для другой конфигурации WSL
можно задать `WSLG_X11_PATH`, `WSL_LIB_PATH`, `WEBOTS_DISPLAY` и
`WEBOTS_GPU_NAME` (по умолчанию `NVIDIA`). GPU-конфигурация не является готовой
конфигурацией для обычного Linux/Xorg или macOS.

`WEBOTS_RENDERER=gpu` завершает запуск с понятной ошибкой, если аппаратного
OpenGL нет. `WEBOTS_RENDERER=auto` пробует OpenGL и при неудаче использует CPU.
Но отсутствие устройства/каталога, указанного в Compose, обнаруживается самим
Docker ещё до запуска программы: на машине без GPU используйте базовую CPU-команду.
Она также переключает существующий проект обратно на CPU, сохраняя volumes.

## Кнопки в дашборде

Откройте «Показать симуляцию» в правой панели:

- **Обычная** — режим Webots `real-time`, целевая скорость около 1×.
- **Максимальная** — режим `fast`, без ограничения реальным временем.

Выделение кнопки меняется после подтверждения симулятора. При потере связи
кнопки недоступны; неподтверждённая команда выдаёт ошибку. Повторное подключение
получает текущее состояние, не повторяет старые команды. Режим общий для всего
симулятора. Закрытие панели не останавливает миссию. После перезапуска контейнера
начальный режим берётся из `WEBOTS_MODE` (`realtime` по умолчанию, также `fast`).

Частота обновления **внешнего вида сцены** настроена на 30 FPS. W3D передаёт
модель и изменения состояния, а браузер рисует их в разрешении панели.
Шаг физики остаётся 16 мс, разрешение камеры робота 320×180, периоды датчиков не меняются.
`WEBOTS_VIEW_FPS` позволяет выбрать целое значение 1–60 перед запуском Compose.
Это не гарантия FPS браузера: движок W3D R2025a ограничивает частоту отрисовки
интервалом не менее 40 мс (потолок около 25 FPS). Скорость физики, обновления W3D
и кадры камеры робота — разные показатели.

Просмотрщик R2025a, WASM и текстуры текущего мира включены во frontend-образ;
браузер не скачивает их с CDN. Сборка проверяет закреплённые хеши ресурсов.
Для локальной разработки сначала выполните `npm run prepare:viewer`;
Docker выполняет этот шаг автоматически. При добавлении текстур нового мира
дополните `docker/webots-viewer-assets.json` и пересоберите frontend.
Адаптер работает в отдельном iframe; закрытие панели освобождает его состояние.
Из upstream удалена автоматическая команда `pause` при загрузке модели:
просмотр не должен останавливать выполняющийся маршрут. Панель инструментов
Webots не создаётся; скорость меняется только нашими кнопками.

## Измерение

При установленном Node.js и зависимостях проекта:

```powershell
node scripts/simulation-benchmark.mjs
```

Скрипт открывает W3D-соединение, проверяет наличие камеры робота,
переключает обычный/максимальный режимы и измеряет отношение прошедшего времени
симуляции к реальному времени по телеметрии. По умолчанию измеряет каждый режим
20 секунд после прогрева; `BENCHMARK_SECONDS` задаёт 5–300 секунд. В конце
восстанавливает обычный режим. Он также выводит число обновлений сцены и объём
данных; это не измерение FPS отрисовки. Откройте панель симуляции в браузере,
чтобы учитывать нагрузку её отрисовки на эту же машину.
Запускайте на тестовом мире без активной миссии,
так как скорость меняется для всех клиентов. Не пересоздавайте сервисы во время замера.

Достижение 1× зависит от CPU/GPU, сцены и датчиков; гарантировать его на любом
компьютере нельзя.

Замер **после перехода на W3D**, 18.09.2026, RTX 3070 Ti / Docker Desktop WSL2:
открытый дашборд, камера включена, робот движется по маршруту.

| Показатель | Результат |
|---|---:|
| Обычная скорость, среднее за 20 с | 0.978× |
| Максимальная скорость, среднее за 20 с | 1.962× |
| Обновления W3D в обычном / максимальном режиме | 23.8 / 26.2 в секунду |
| Отрисовка браузера при движении, выборка 10 с | 19.4 FPS |

В ожидании маршрута отдельная выборка отрисовки дала 22.5 FPS. Частота отрисовки
измерялась по вызовам `WrenRenderer.render`, а не по частоте WebSocket или
`requestAnimationFrame`. Это локальные измерения на одной машине, а не гарантии.
Тестовый маршрут после замера отменён. CPU fallback и GPU отдельно прошли полный
контейнерный smoke-test; также прошли 268 тестов, ESLint и сборка frontend-образа.
В браузере проверены смена скорости, закрытие панели и восстановление после
разрыва сокета; положение неподвижного робота после подключения совпало с телеметрией.

Исторический замер **до перехода на W3D**, 18.09.2026: Docker Desktop/WSL2, RTX 3070 Ti, мир
`youbot_only.wbt`, камера робота и внешний MJPEG 960×540 включены. Каждый режим
измерен 20 секунд; значения — средняя скорость симуляции, не FPS.

| Конфигурация | Обычная | Максимальная |
|---|---:|---:|
| Исходная CPU, внешний вид 60 FPS | 0.47× | 0.45× |
| CPU, внешний вид 10 FPS | 0.79× | 1.68× |
| GPU WSLg, внешний вид 10 FPS | 1.02× | 1.48× |

Таблица выше измерена при ожидании маршрута. Дополнительный GPU-замер во время
выполнения маршрута длиной 15 м: **1.03× обычная / 1.36× максимальная**,
оба видеопотока включены, обратная связь миссии свежая.

GPU существенно снизил нагрузку CPU (примерно с пяти ядер до одного), но не
оказался быстрее CPU во всех режимах: WSLg добавляет стоимость передачи кадров.
Это измерения текущей сцены на одном компьютере, а не гарантия для сложных миров.
Для плавного реального времени на проверенной машине рекомендуется GPU;
CPU-режим остаётся полноценным вариантом, особенно с кнопкой «Максимальная».

Полный контейнерный smoke-test: `node scripts/full-container-smoke-test.mjs`.
Он проверяет W3D, локальный WASM, камеру, физическое выполнение миссий,
смену скорости, перезапуск route и отмену после перезапуска симулятора.
GPU-вариант выбирается переменной `SIMULATOR_GPU=1`. Перед тестом остановите
основной стек, чтобы освободить порты; тест использует собственные volumes.

Основание GPU-конфигурации: [WSLg containers](https://github.com/microsoft/wslg/blob/main/samples/container/Containers.md).

Протокол и просмотрщик: [Webots R2025a streaming](https://github.com/cyberbotics/webots/blob/R2025a/docs/guide/web-streaming.md),
[Web scene](https://github.com/cyberbotics/webots/blob/R2025a/docs/guide/web-scene.md).
