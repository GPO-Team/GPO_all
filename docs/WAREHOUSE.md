# Адресное хранение и подготовка размещения

Страница `/warehouse` — отдельный модуль подготовки складских операций. На ней
можно описать многоуровневые стеллажи, зарегистрировать коробки на приёмке,
подобрать ячейку и зарезервировать её подготовленным заданием.

## Запуск

Нужен Node.js 22.19+ и установленные зависимости (`npm ci`). В разных терминалах:

```powershell
npm run service:route
npm run dev
```

Открыть `http://127.0.0.1:5173/warehouse` или перейти по ссылке «Склад» с главной
страницы. При уже запущенном `npm run bridge` повторно запускать route-сервис
не нужно. Для редактирования склада Webots, gateway и native solver не нужны;
их готовность не является условием работы складского API.

Frontend использует тот же адрес backend, что и API миссий:
`VITE_MISSION_URL`, по умолчанию `http://127.0.0.1:9002`.

## Первый сценарий

1. Создать стеллаж, задать его код, положение, поворот, число секций и мест в
   секции. Для каждого уровня задать высоту опоры, свободную высоту и предельную
   массу **одной ячейки**. Примерные значения в форме можно изменить; они не
   описывают подтверждённые возможности робота.
2. Посмотреть расположение стеллажа на плане сверху и выбрать его. Вид спереди
   показывает секции, уровни и адреса ячеек.
3. Зарегистрировать конкретную коробку на приёмке: уникальный ID, название,
   ширину, глубину, высоту и массу.
4. Запросить подбор места. Система объяснит причины отказа для неподходящих
   ячеек. Выбрать подходящую и подготовить задание размещения.
5. Убедиться, что ячейка зарезервирована, а коробка по-прежнему находится на
   приёмке. Перезагрузить страницу — состояние сохранится на сервере.
6. При необходимости отменить подготовленное задание. Его бронь будет снята,
   а запись об отмене останется в списке заданий.

Ячейки можно выбирать клавиатурой: Tab переводит фокус внутрь стеллажа,
стрелки перемещают его между местами и уровнями, Home/End — к краям уровня.
Широкие уровни прокручиваются внутри панели, в том числе на узком экране.

## Координаты и вместимость

- X/Y — координаты центра стеллажа в плоскости мира, метры. Поворот в форме
  задаётся в градусах, а в API/JSON хранится в радианах. Положительный поворот —
  против часовой стрелки, как в координатном контракте проекта.
- Секции идут по локальной оси X стеллажа; глубина — по локальной Y.
- Адрес `A-02-03-01` означает: стеллаж A, секция 2, уровень 3, место 1.
  Внутренний ID ячейки основан на ID стеллажа и индексах, а не на названии.
- Высота опоры — поверхность полки. Она отличается от высоты центра коробки и
  от положения TCP манипулятора.
- Одна ячейка вмещает одну коробку, хранение в один ряд по глубине. Коробка
  сохраняет заданную ориентацию относительно стеллажа; автоматический поворот
  для подбора не выполняется.
- Для размещения требуется 1 см свободного места с каждой горизонтальной
  стороны и 1 см сверху. Масса не должна превышать предел ячейки.
- Стеллажи должны помещаться в границы карты и не пересекаться друг с другом.

Пределы первой версии: 20 стеллажей, до 12 секций, 8 мест в секции и 12 уровней;
суммарно не более 1000 ячеек. Эти ограничения относятся к редактору. Поддержка
высоты или массы в редакторе не подтверждает возможность работы текущего робота.

Приёмка и выдача в этой версии — логические площадки с настраиваемыми именами
и координатами. Регистрация коробки не создаёт объект Webots и не означает
измерение его физического положения.

## Сохранение и конфликты

Состояние хранится в отдельной SQLite-базе внутри
`<MISSION_STATE_DIR>/warehouse/records.sqlite`; по умолчанию это
`data/missions/warehouse/records.sqlite`. Оно не попадает в историю миссий
робота. Порт хранилища отделён от логики склада, чтобы впоследствии подключить
согласованный PostgreSQL-адаптер.

Сервер проверяет ревизию данных и резервирует коробку вместе с ячейкой.
Два клиента не смогут подготовить конкурирующие задания на одно место или
одну коробку. При изменении данных в другой вкладке нужно обновить состояние
и повторно проверить выбор. Сохранение выполняется до подтверждения запроса.
Если редактируемый стеллаж или настройки площадок изменились в другой вкладке,
черновик сохраняется для просмотра, но запись поверх изменённых данных
блокируется до явной загрузки актуальной версии.

Повторная доставка того же ID задания не создаёт второе задание. Отменённое
задание повторным запросом не запускается заново.
Запросы frontend ограничены 15 секундами; после неопределённого результата
сначала обновите данные. Повреждённое сохранённое состояние не заменяется
пустым складом автоматически: сервис вернёт ошибку для восстановления из копии.

Экспорт/импорт JSON предназначен для **схемы склада**: стеллажей и площадок.
Он не переносит коробки и историю заданий. Импорт схемы при действующих
подготовленных заданиях запрещён. Для полной резервной копии остановить
route-сервис/bridge и скопировать весь каталог `warehouse` вместе с файлами
SQLite. Не заменять базу при работающем сервисе.

## Граница физического исполнения

Подбор подтверждает геометрическую вместимость и допустимую массу. Доступ
робота к ячейке имеет статус «не проверен» — подход, работа между полками,
захват и опора на полку ещё должны быть подтверждены отдельно.

Подготовленные задания не отправляются роботу, не переводятся в выполненные
по таймеру и не меняют адрес коробки. Складской модуль не меняет контроллер,
кинематику, сцены Webots и существующие миссии. Будущая интеграция должна
связать складское задание с отдельной попыткой исполнения и обновлять учёт
только по подтверждённому результату размещения.

## Проверки

```powershell
npm test
npm run lint
npm run build
npm run test:bridge
npm run test:services
```

Новые тесты проверяют геометрию повёрнутых стеллажей, адресацию, вместимость,
конфликты ревизий и резервирования, повторную доставку запросов, сохранение,
HTTP-контракт и пользовательский сценарий подготовки размещения.
